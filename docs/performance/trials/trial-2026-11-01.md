# Full trial of the web features added since 2026-10-29 - 2026-11-01

State of `main` after PRs #99 to #107 (forms, handoffs, share links, reopening,
chat comfort, real M2/M4/EV1/X5 in the web, left sidebar, calmer chat), tried
with the real model for the first time. Previous trials:
[2026-10-13](trial-2026-10-13.md), [2026-10-14](trial-2026-10-14.md),
[2026-10-24](trial-2026-10-24.md).

## Machine and method

- **Model**: `qwen3-coder:30b` and `bge-m3` served by Ollama 0.40.13 on a RunPod
  pod (24 GB GPU), through RunPod's HTTP proxy. The pod address is not in the repository.
- **Client**: Linux workstation, Python 3.12, Docker 29.9.1 for the sandbox,
  headless Chromium (Playwright) for the interface.
- **Project**: a throwaway folder with `stats.py` (`moyenne` crashes on an empty
  list), `notes.md`, a few-shot file (`exemples.jsonl`, 2 examples,
  `fewshot_min_score` 0.6) and, for the global run, `deploiement.txt` holding a
  fake AWS key. Throwaway data folder; `~/.sensai` not touched.
- **Three passes**:
  1. one scenario per feature through the real `sensai-web` API (a script that
     answers confirmations and forms, and records every SSE event);
  2. the same features in the browser (real interface, real server, real model);
  3. a global run: one long conversation mixing the features, then the same
     session resumed in the terminal, then a task created in the web and run
     by `sensai-schedule`.
- One measurement per scenario: orders of magnitude, not benchmarks.

## Findings

1. **Project index never refreshed during a session (bug, fixed in #108).**
   `sensai-web` and the CLI indexed the project only at the first question. A
   file created or modified afterwards (often by the agent) stayed invisible to
   the search, and the model answered that it did not exist - three times in a
   row, even when told to call `read_file`. A server restart made it work, which
   proved the cause. Fix: `RagIndex.refresh_if_stale` re-runs the incremental
   update at most every 30 s before a search; checked with the real model.
2. **The team can validate a change made in the wrong file (not fixed).** The
   developer wrote `src/sensai/stats.py` (a path that does not exist in the
   project, probably inspired by the agent's name) and the reviewer said
   "approved"; the main agent then told the user `stats.py` was updated. Possible
   fix: give the reviewer the files the task names and make it check that the
   written paths match; refuse to create a file whose name already exists
   elsewhere in the project.
3. **A French few-shot example can override a language preference** once
   (A7 vs M1). Without a matching example, the preference was respected.
4. **Deleting a conversation keeps the facts saved during it (M3).** A test word
   saved by the agent in a conversation that was then deleted was recalled in
   other conversations. Facts are project-wide by design; the sidebar's delete
   does not say so.
5. **Repeated answer text.** The model sometimes writes its answer, calls a tool,
   then writes the answer again; the saved answer contains both, glued without
   a space ("…file.The file…"). The interface adds a paragraph break, the
   saved session does not.
6. **Invention when information is missing.** In the terminal, asked for a value
   that had never been read in the session, the model invented one instead of
   saying it did not know (the system prompt asks it to say so).
7. **Unanswered form**: expired after 100 s; the agent then said what was
   missing. Expected behaviour.

## Later the same day: the model did not know the date

Reported by the team: asked about 2026, the agent thought it was 2024 and called
recent `web_search` results wrong. Reproduced with `qwen3-coder:30b` in the CLI:
"We are currently in 2024", then Python 3.15.2 (2026) found by the search
was called "wrong or outdated" and replaced by 3.12.4 (2024) from memory.
Cause: the date was never given to the model, and web results are fenced as
`trust="untrusted"` (meant against injected instructions, read as "false").
Fix: `build_system_prompt` adds today's date with a rule (recent facts from
`web_search` and project files beat the training memory; "untrusted" does not mean
false), and `web_search` results say when they were searched. Re-check, same
question: "We are in 2026", then "the latest stable version of Python is
3.15.2, released on 25 October 2026". `sensai-schedule` then got the same date block, computed at each task run
(a `loop` can run for days).

Follow-up the same day (#45): asked for the time, the model searched the web and
gave a wrong hour, because search snippets are cached by the search engine. Fix
(branch `chore/time-ev4-adr`, not yet re-checked with the real model): the date
block now also gives the local time at the start of the conversation, with its
UTC offset, and the `web_search` description says snippets may be old and that
the date in the instructions wins. The web server keeps that time per
conversation: a time changing at every turn would change the start of the
prompt, and Ollama would re-read the whole conversation each turn. Limit: in a
long conversation, the time given is the start time, not the current one; the
MCP `time` server gives the current one when configured.
