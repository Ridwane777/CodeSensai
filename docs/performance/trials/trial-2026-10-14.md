## Incident: interrupted indexing
The first indexing (195 files) stopped at file 29: an embeddings call did not
answer within 300 s. The neighboring files, retried alone, pass in under 6 s:
a transient pod or proxy failure, not the code. The CLI reacted as designed
(ADR-0013): search turned off for the session, tool answering "Search
unavailable", no crash. The second run resumed the index where it had
stopped and finished it (8 min 08 s including the question). ⚠️ The model
left a `<tool_call>` tag in its final answer during the first run.

## What blocks the end-to-end demo
1. **The agent has only one tool out of five.** Only `search_codebase` is
   registered (`cli.py`). `run_code`, `read_file`, `write_file` and
   `web_search` exist but are offered neither by the CLI nor by the shared
   registry (`src/sensai/registry.py`, empty), used by `sensai-schedule`. The
   model can neither run code nor read a file in conversation.
2. **OUT-15 (EV4, high severity)**: the CLI gateway is built without
   `input_guards` or `output_filters` (`cli.py:205`). Passages returned by
   `search_codebase` reach the model without secret masking.

Both points are fixed on the same branch as this report (shared registry and
guardrails on the CLI and scheduler gateways), then a new trial is recorded
below.

## Limits
- One measurement per scenario: orders of magnitude.
- In the first run, Workstream B tools are called without the model (point
  4): they were not offered to it yet. The second run has the model call
  them.
- The quality of RAG citations and of the EV1 judge is only seen on a few
  questions.
