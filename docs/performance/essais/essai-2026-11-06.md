# Trial 2026-11-06: every feature with qwen3:8b on the development laptop

Until now, features were checked with the real model on a RunPod GPU
(`qwen3-coder:30b`). This trial plays one scenario per feature with the
**default development model, `qwen3:8b`, on the team laptop, CPU only**: the
setup a developer actually has, and the one the README tells people to install.

## Set-up

| | |
| --- | --- |
| Machine | Laptop, Intel Core i7-1355U (12 threads), 14 GiB RAM, **no GPU**, Ubuntu 26.04.1 |
| Software | Python 3.12.3, Ollama 0.20.0, Docker 29.9.1 (images `python:3.12-slim`, `sensai-browser`) |
| Model | `qwen3:8b` (8.2 B parameters, Q4_K_M), `config.json` of the repository (temperature 0.2, `num_ctx` 8192) |
| Script | [`scripts/essai_features.py`](../../../scripts/essai_features.py), reproducible: `python scripts/essai_features.py --out results.json` |
| Raw results | [`features-qwen3-8b-2026-11-06.json`](../data/features-qwen3-8b-2026-11-06.json), A2 with longer delays: [`features-a2-qwen3-8b-2026-11-06.json`](../data/features-a2-qwen3-8b-2026-11-06.json) |

**Method.** The script builds a throwaway git project (`stats.py` with
`moyenne`, which divides by zero on an empty list, and `maximum`; one passing
test), with its own `SENSAI_HOME`, so neither the repository nor `~/.sensai`
is touched. Each scenario comes from the feature's user stories and has an
observable check (text on screen, file written, HTTP answer); its duration is
measured. The CLI is driven through a pipe (confirmations typed as `o` / `n`),
the web through `sensai-web`'s API (SSE stream, `/confirm`, `/answer`). RAG is
off (`--no-rag`) except where it is the feature under test. A local MCP server
(`tests/tools/fake_mcp_server.py`) is plugged in for T1.

**Not covered.** R1/R2, A6 and A7 need the `bge-m3` embedding model, whose
download (1.2 GB at ~0.3 MB/s) was stopped at 31 %. They are still to be run.

**Order of magnitude.** On this CPU one ordinary question takes **7 to 11
minutes**: the model first reads several thousand prompt tokens (system
prompt, tools) at about 10 tokens/s, then thinks (`qwen3` writes a long
reasoning before answering). The commands that do not call the model answer
in under a second. The laptop is usable to check that a feature works, not to
work with the agent day to day.

## Issues found

### Fixed during the trial

- **Every turn failed on CPU: fixed Ollama timeout.** The client waited 60 s
  (`timeout=60`, hard-coded in `core/ollama_client.py`) for the first byte;
  reading the prompt alone takes several minutes here. The first scenario
  ended on "Ollama ne répond pas (timeout)". Now a 10 s connect timeout (a
  stopped Ollama is still reported at once) and a read timeout set by
  `request_timeout` in `config.json` or `--request-timeout`, **600 s by
  default**. The error message says what to raise. Never seen before because
  every earlier trial ran on a GPU.
- **Sub-agents cut after 120 s: delegation delay now configurable.**
  `team_task` and `delegate_task` stopped after `DELEGATION_TIMEOUT_S = 120`,
  shorter than one model call on this CPU. It can now be set with
  `"tools": {"delegation_timeout_s": …}` in `config.json`. **The default stays
  120 s** (team decision). `tool_timeout_s` (120 s) still caps every tool call,
  so both must be raised:
  `"tools": {"tool_timeout_s": 1800, "delegation_timeout_s": 1800}`.

### Still failing, model quality

- **T5, a well-formed but wrong answer.** Asked which function computes an
  average, `qwen3:8b` did not read the project: it took its own tool list for
  the project's functions and answered
  `{"fonction": "mcp_calc_add", "fichier": "non spécifié (…)"}`. The schema was
  respected; the content was wrong. Likely made worse by the trial set-up (RAG
  off, MCP tools named `add`, `fail`…). The same feature was measured right
  with `qwen3-coder:30b` ([T5-structured.md](../T5-structured.md)).
- **A2, the team does not finish the task.** With 120 s, the team was cut
  every time; the main agent then wrote the test itself, with an invented
  import (`from your_module.utils import moyenne`) or without
  `import pytest`: the test fails. Rerun with 1800 s: `team_task` ran to the
  end (10 min 16, not cut), **but changed no file**; the main agent then said
  "`moyenne.py` does not exist" and asked for paths, although `stats.py` holds
  only two functions. The longer delay is **needed** on CPU but **not
  enough**: with an 8 B model the team does not complete. The same task passed
  with `qwen3-coder:30b` on 2026-11-03 ([essai-2026-11-03.md](essai-2026-11-03.md)).

### To improve

- **Unknown top-level keys in `config.json` are ignored.** The first A2 rerun
  wrote `"tool_preferences"` (the internal name) instead of `"tools"`: no
  error, the 120 s default applied. A typo inside `"tools"` stops the start-up;
  one at the top level should too.
- **Trial script.** Seven scenarios first failed because of the script, not
  the product (key `session_id`, event `confirm_request`, form field `id`,
  `at_message` for a fork, `?session=` for the journal, a non-existent
  `list_files` tool in X5). Fixed and rerun; the JSON marks each rerun with
  its reason (`rerun`). Two limits remain: the `o` lines typed in advance
  become new messages when no confirmation is asked (three useless 30-minute
  turns in A2), and only the last 3,000 characters of output are kept, which
  lost the team's own report in A2.

## What this changes

- The development set-up described in the README now works on a laptop
  without a GPU, slowly. Before the fix, no question could get an answer.
- 23 of 25 scenarios pass with the small model; T5 and A2 need a larger model
  to give right answers. The README should say so instead of presenting
  `qwen3:8b` as enough for everything.
- Next: run R1/R2, A6 and A7 once `bge-m3` is downloaded; run A2 and T5 again
  with RAG on to see how much of the failure it explains.
